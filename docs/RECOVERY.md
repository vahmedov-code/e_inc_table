# Диагностика повторяющихся перезапусков

Повторная запись той же версии не устанавливает причину неисправности. Для диагностики добавлена отдельная среда **esp32-m075-recovery**, версия **0.1.1-recovery**.

В recovery аппаратный драйвер дисплея и его задача исключены при компиляции. Нет инициализации SPI, выделения кадрового буфера, монтирования или форматирования LittleFS. Не выполняется подключение к сохранённой офисной сети, NTP или mDNS: работает только локальная точка доступа с пониженной мощностью передатчика. Ключ API и пароль точки доступа читаются из прежних настроек. Записывающие маршруты API отвечают HTTP 423, в том числе включение дисплея, форматирование, Wi-Fi, расписание и загрузка кадров. Сохранённое разрешение дисплея игнорируется без удаления из NVS.

Старое изображение может остаться на e-ink: recovery **не очищает экран**, поскольку это тоже потребовало бы работы драйвера.

Защита от пониженного напряжения и watchdog не отключаются. Версия не доказывает исправность питания и не заменяет проверку аппаратуры.

## Обновить исходники и собрать

В терминале PlatformIO, из папки проекта:

```powershell
git pull --ff-only
pio run -e esp32-m075-recovery
```

Если Git сообщает о локальных изменениях, не сбрасывайте их: сохраните результат ошибки и проверьте изменения. Обычная кнопка Build по-прежнему собирает основную среду esp32-m075-v3; для диагностики нужна команда с указанным -e.

## Загрузка владельцем локально

Закройте Serial Monitor. Сначала выполните проверку без записи:

```powershell
$backupHash = (Get-FileHash 'C:\AviorSign\gooddisplay_factory_backup.bin' -Algorithm SHA256).Hash
& "$env:USERPROFILE\.platformio\penv\Scripts\python.exe" tools/safe_flash.py --environment esp32-m075-recovery --backup 'C:\AviorSign\gooddisplay_factory_backup.bin' --sha256 $backupHash
```

После успешной проверки запустите загрузку, подставив актуальный COM-порт:

```powershell
& "$env:USERPROFILE\.platformio\penv\Scripts\python.exe" tools/safe_flash.py --environment esp32-m075-recovery --backup 'C:\AviorSign\gooddisplay_factory_backup.bin' --sha256 $backupHash --port COM20 --write
```

Подтверждение: **FLASH AVIOR RECOVERY**. Загрузка заменяет приложение, загрузчик, таблицу разделов и выбор OTA по тем же смещениям, что описаны в основном README. Полное стирание Flash и форматирование не выполняются. Бэкап остаётся вне репозитория. Агент не выполняет запись на устройство удалённо.

## Получить журнал

```powershell
pio device monitor --port COM20 --baud 115200
```

Даже если стартовый вывод был пропущен, каждые 5 секунд появляется строка:

```text
[health] mode=recovery uptime_s=5 heap=... min_heap=... clients=0 reset=power_on(1)
```

Скройте AP password и API token перед отправкой стартового вывода. Строки health секретов не содержат.

- Если uptime_s растёт 5, 10, 15 и далее, ESP32 продолжает работать.
- Если снова появляются boot/phase или uptime возвращается к началу, произошёл новый запуск.
- reset=brownout указывает на срабатывание защиты по напряжению; полный обрыв питания может отображаться как power_on, поэтому power_on не исключает неисправность питания.
- panic или watchdog требует анализа полного журнала/Backtrace.
- Если USB-порт исчезает, а связь по Wi-Fi и uptime продолжаются, отдельно проверяйте USB-кабель, разъём и CH340.
- Стабильность recovery лишь сужает круг причин: он одновременно исключает дисплей, файловую систему и STA-подключение. Это ещё не доказательство ошибки конкретного компонента.

После загрузки оставьте устройство на 1–2 минуты и соберите журнал. Возвращение к обычной среде и повторное включение дисплея выполняйте после выяснения причины. Основная среда также получает причину сброса, этапы запуска и heartbeat, но сохранённое разрешение дисплея в ней продолжает действовать.

Причина сброса берётся через [официальный ESP-IDF esp_reset_reason()](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/misc_system_api.html#reset-reason).
